WHAT IS THIS FILE FOR?
----------------------
This file lists the problems found in the project's design documents:
  - LEARNING_PLANNER.md
  - LEARNING_ORCHESTRATOR.md
  - TUTOR.md
  - ASSESSMENT.md
  - the code scaffold in agentic-learning-platform/

It was written while ASSESSMENT.md was being created. After that, the whole
repository was read again to check it.

Use this file to:
  1. see what must be decided before anyone writes code (Part 2);
  2. find where each problem is, by file and line (Part 3);
  3. see which decisions are waiting for the project owner (Part 4);
  4. look at suggested fixes (Part 6). These are suggestions only. Check
     them before using them.

This file does NOT change any spec. Nothing listed here has been applied.


HOW TO READ AN ENTRY
--------------------
  R-001  [Critical]  Short title
    Problem: what is wrong
    Where:   file and line(s) where you can see it
    Why it matters: what goes wrong if it is ignored

  Severity:
    Critical  blocks several components from being built
    High      must be decided before building the part it affects
    Medium    should be decided before that part is finished
    Low       cleanup or a small clarification

  - IDs never change. ASSESSMENT.md refers to them (for example "R-001").
  - Entries are grouped by topic, so the numbers are not in order.
  - Line numbers match the files at commit 265c4bb. The Planner,
    Orchestrator and Tutor specs have not changed since commit c466657.


===============================================================================
 PART 1 - SUMMARY
===============================================================================

Where the project stands
  - Specs exist for the Planner, Orchestrator (Curator), Tutor and
    Assessment Engine.
  - There is no separate spec for Learning Context, the shared teaching
    library, the database, the API or the stack.
  - No code exists. The 54 files under agentic-learning-platform/ are empty
    (all .py files, requirements.txt, docs/*.md, AGENTS.md, README.md,
    ORCHESTRATOR.md), except the four AGENT.md files.
  - Those four AGENT.md files are exact copies of the root specs. One of
    them is in the wrong folder (R-043).

Issue count
  61 issues: 1 Critical, 7 High, 33 Medium, 20 Low.
  60 are open. 1 is resolved (R-045).

Is the project ready to implement?
  Not yet. The design is consistent on its main rules:
    - only the Orchestrator writes to the database;
    - agents never call each other;
    - answer keys are never shown during an attempt;
    - grades come only from the saved rubric.
  But about seven decisions must be made first (Part 2). Without them,
  code would be written against contracts that will change.

-------------------------------------------------------------------------------
 3.1  Contracts between the agents
-------------------------------------------------------------------------------

R-001  [Critical]  Objective IDs are used everywhere, but nothing creates them
  Problem: The Orchestrator, Tutor and Assessment all work per "objective"
    (objective_id). The Planner only outputs topics (with IDs) and
    course-level "expected outcomes". No spec says:
      - what an objective is;
      - who gives it an ID;
      - how it links to topics.
  Where:
    - LEARNING_PLANNER.md sec 6. Its own text still mentions "objectives"
      at lines 23, 42 and 111.
    - LEARNING_ORCHESTRATOR.md lines 57, 68 and 85-87.
    - TUTOR.md lines 51 and 115.
    - ASSESSMENT.md sec 5, where it is marked "provisional".
  Why it matters: Teaching targets, assessment coverage, evidence,
    remediation and the database all need this key. Quietly using topic
    IDs instead would hide a design decision.

R-002  [High]  The pre-planning diagnostic has no place in the current flow
  Problem: The diagnostic runs between preview_goal and build_curriculum.
    However:
      - build_curriculum has no input for its results;
      - the Orchestrator workflow goes straight from preview to
        curriculum.
  Where:
    - LEARNING_PLANNER.md line 40, and sec 7 lines 63-64.
    - LEARNING_ORCHESTRATOR.md line 52, line 93 (workflow step 1) and
      line 130 (acceptance criterion 1).
  Why it matters: The diagnostic cannot influence the plan. Developers
    might also connect Assessment directly to the Planner, which breaks the
    "agents only talk through the Orchestrator" rule.

R-003  [High]  start_assessment cannot start a diagnostic
  Problem: start_assessment needs a Session ID. Sessions are only created
    by open_course, which happens after a curriculum exists. The list of
    allowed assessment "purposes" is also never written down.
  Where: LEARNING_ORCHESTRATOR.md lines 57, 68 and 72.
  Why it matters: There is no way to start the diagnostic.

R-053  [Medium]  The Orchestrator treats every graded attempt as
       progression
  Problem: The report protocol always "applies the progression policy" to
    a graded result. Diagnostic results must never do this.
  Where: LEARNING_ORCHESTRATOR.md lines 87 and 97.
  Why it matters: A diagnostic could unlock courses by mistake.

R-004  [High]  There is no evidence type for diagnostic results
  Problem: The Orchestrator knows three kinds of evidence:
      - self-report;
      - Tutor observations;
      - graded results.
    Diagnostic answers fit none of them. They are real answers, so they
    are not self-report, but they must not count as course grades.
  Where:
    - LEARNING_ORCHESTRATOR.md line 103.
    - LEARNING_PLANNER.md line 59, where the "kind of evidence" is not
      listed.
  Why it matters: Stored as grades, diagnostic results could unlock
    courses. Stored as self-report, their value is lost.

R-005  [High]  Is Learning Context an agent or a record?
  Problem: The specs disagree.
    - The Orchestrator says Learning Context is a record it keeps, and that
      it is the only writer. It says this overrides the Planner.
    - The Planner's table still says "Learning Context" persists the data.
    - The scaffold has agents/learning_context/agent.py, prompts.py and a
      test file, which looks like an AI agent.
  Where:
    - LEARNING_PLANNER.md line 21.
    - LEARNING_ORCHESTRATOR.md lines 7 and 28.
    - The agents/learning_context/ folder.
    - transcript_temp.txt lines 568-576.
  Why it matters: Different developers will build different things.

R-006  [Medium]  Who fetches teaching material?
  Problem: The specs give different answers.
    - The Tutor says it searches the shared library itself.
    - The Orchestrator says it supplies the inputs.
    - ASSESSMENT.md follows the Tutor.
  Where:
    - TUTOR.md lines 15 and 90.
    - LEARNING_ORCHESTRATOR.md lines 7 and 114.
    - ASSESSMENT.md sec 7 step 3.
  Why it matters: It changes how the library service is built and how
    strictly "only the Orchestrator coordinates" is read.

R-007  [Medium]  Old decisions in the transcript are not marked as replaced
  Problem: transcript_temp.txt says three things that later specs changed:
    - the Tutor switches teaching method (it is now the Orchestrator);
    - "Learning Context AI" is the only writer (it is now the
      Orchestrator);
    - a 5-10 question quiz runs before the curriculum. This was replaced by
      the course-entry familiarity chat, and is now partly brought back as
      the optional diagnostic.
    No document records these changes.
  Where:
    - transcript_temp.txt lines 373-387, 436-454 and 568-576.
    - LEARNING_ORCHESTRATOR.md lines 13 and 102.
    - LEARNING_PLANNER.md line 80.
  Why it matters: Anyone reading the transcript gets the wrong design.

R-008  [Medium]  The grading request carries learner context
  Problem: The Orchestrator sends "learner context relevant to feedback"
    in the same request as grading. The rule says context must not affect
    the grade, but inside one AI call it can.
  Where:
    - LEARNING_ORCHESTRATOR.md lines 96 and 105.
    - ASSESSMENT.md sec 5, which allows only a separate "feedback context".
  Why it matters: Grades could be biased by what the system knows about
    the learner.

R-009  [Medium]  The teaching method is not passed to Assessment, and no
       list of methods exists
  Problem: The owner wants assessment to be informed by the teaching method
    (the "pedagogical model"). However:
      - the Orchestrator does not send it to Assessment;
      - it is chosen per objective, so one course can use several;
      - no registry of models exists.
  Where:
    - LEARNING_ORCHESTRATOR.md lines 13 and 96.
    - TUTOR.md line 118.
    - ASSESSMENT.md sec 5.
  Why it matters: A contract field is missing, and the Tutor also depends
    on the missing registry.

R-051  [Medium]  ASSESSMENT.md needs fields the Orchestrator does not yet
       send or store
  Problem: The missing fields are:
    - inputs: assessment policy, excluded items, entry path (skipped or
      studied), pedagogical context, selection and feedback context, and a
      goal-preview reference for the diagnostic;
    - outputs: separate learner and grading parts of a prepared report,
      criterion judgements, evidence type and basis, recommended next
      action, the diagnostic planning summary, and issue codes;
    - action names: prepare_assessment and grade_submission. The
      Orchestrator only names the learner actions start_assessment and
      submit_assessment.
  Where:
    - ASSESSMENT.md secs 5-6.
    - LEARNING_ORCHESTRATOR.md secs 5-7 and lines 83-87.
  Why it matters: The two specs will not match in code.

R-054  [Low]  The Orchestrator has no rule for a failed assessment
       preparation
  Problem: The Orchestrator's failure table covers grading timeouts. It
    does not cover preparation failing, for example when a target cannot
    be grounded in sources or there is not enough material.
  Where: LEARNING_ORCHESTRATOR.md sec 10 (lines 117-126).
  Why it matters: It is unclear what the learner sees, or whether the
    Planner should be asked to review.


-------------------------------------------------------------------------------
 3.2  Assessment rules that are still open
-------------------------------------------------------------------------------

R-010  [High]  "Pass" is not defined
  Problem: No spec says how a course assessment is passed. Open questions:
    - Must every mandatory objective be shown?
    - Is there a percentage?
    - How do partial or unclear results count?
    ASSESSMENT.md proposes a rule: every mandatory target must be
    "demonstrated", and unclear results are "inconclusive", never pass or
    fail.
  Where:
    - LEARNING_ORCHESTRATOR.md lines 87 and 97.
    - ASSESSMENT.md sec 8.
  Why it matters: Course unlocking depends on it.

R-011  [Medium]  The pass rule could be defined in two places; the owner of
       the policy is unclear
  Problem: Assessment returns an outcome per attempt. The Orchestrator
    decides progression. If both define "pass", the two can drift apart.
    Nobody owns the "assessment policy" (pass rule, coverage minimum,
    diagnostic size).
  Where: LEARNING_ORCHESTRATOR.md lines 87 and 106; ASSESSMENT.md sec 9.
  Why it matters: Two definitions of pass would give inconsistent
    unlocks.

R-012  [Medium]  The attempt lifecycle is not defined
  Problem: Three things are missing:
    - attempt states (prepared, shown, submitted, grading, graded,
      abandoned);
    - whether the attempt ID exists before Assessment is called;
    - which version is kept when preparation is retried, since a retry can
      produce different questions.
  Where: LEARNING_ORCHESTRATOR.md lines 72, 96, 123 and 126.
  Why it matters: Retries and resumes could duplicate or lose attempts.

R-013  [Medium]  "Depth" has no defined values
  Problem: Every spec uses "depth", but no scale exists.
  Where:
    - LEARNING_PLANNER.md lines 12, 57 and 79.
    - TUTOR.md lines 12, 51 and 99.
  Why it matters: Question difficulty and the Planner's "covered at the
    required depth" rule cannot be checked.

R-014  [Medium]  "How the learner will demonstrate the outcomes" is free
       text
  Problem: This is the Planner output that matters most for assessment,
    but it has no structure.
  Where: LEARNING_PLANNER.md line 57.
  Why it matters: Matching question types to objectives cannot be checked.

R-015  [Medium]  The carry-forward rule is not defined
  Problem: The Orchestrator says evidence carries forward "when the rubric
    permits it", but no rubric field says so. It is also unclear whether a
    targeted check can count toward finishing a course.
  Where: LEARNING_ORCHESTRATOR.md line 104; ASSESSMENT.md sec 8.
  Why it matters: Learners may be re-tested on things they already showed,
    or let through without enough evidence.

R-016  [Medium]  The "fresh question" check ignores Tutor practice
       exercises
  Problem: A re-check question could match an exercise the Tutor just
    walked the learner through.
  Where: TUTOR.md line 75; LEARNING_ORCHESTRATOR.md line 104.
  Why it matters: The re-check would not be a real test.

R-017  [Medium]  Can learners see the correct answers after grading?
  Problem: No spec says. The keys are hidden during an attempt, but what
    happens afterwards is undefined.
  Where: LEARNING_ORCHESTRATOR.md line 105; TUTOR.md line 56;
    ASSESSMENT.md sec 6.
  Why it matters: Feedback quality and question reuse both depend on it.

R-018  [Medium]  The skip path and skip threshold are still open
  Problem: The Planner and Orchestrator both mark the skip rule as
    undecided. ASSESSMENT.md proposes that a learner who skips takes the
    same course assessment as everyone else.
  Where: LEARNING_PLANNER.md line 83; LEARNING_ORCHESTRATOR.md line 106.
  Why it matters: Self-reported knowledge could open courses unchecked.

R-019  [Medium]  There are no rules for conflicting evidence
  Problem: Nothing says what happens in these cases:
    - a diagnostic disagrees with a later course result;
    - a pass is followed by a failed targeted check;
    - re-check results are unclear.
  Where: LEARNING_ORCHESTRATOR.md line 103.
  Why it matters: Progression decisions become unpredictable.

R-020  [High]  AI grading of open answers can be inconsistent
  Problem: The same written answer may get a different judgement when it
    is graded again. The MVP limits this in four ways:
      - closed answers are checked by fixed rules;
      - written answers are compared against saved rubric levels;
      - "unscorable" is used when unclear;
      - only the first accepted grade counts.
    The variation is not fully removed.
  Where: no spec covers grader reliability. ASSESSMENT.md sec 8. The
    IntelliCode paper also notes this (PDF p. 7).
  Why it matters: Two learners, or two retries, could be graded
    differently.

R-021  [Medium]  Automatic checking cannot be assumed for every subject
  Problem: The platform covers any subject. Code tests or automatic
    checking of open answers do not work for physics proofs or history
    essays.
  Where: ASSESSMENT.md sec 8.
  Why it matters: Expecting automatic grading everywhere would fail.

R-022  [Medium]  One question per objective is weak evidence
  Problem: ASSESSMENT.md proposes at least one question per mandatory
    objective, and at least one written answer for "apply" or "explain"
    objectives. A single item, especially multiple choice, can be guessed.
  Where: ASSESSMENT.md sec 8.
  Why it matters: Learners could pass on luck.

R-023  [Medium]  Fresh questions cannot be fully guaranteed
  Problem: Comparing questions by fingerprint and values catches repeats
    but not every clever rewording. Some objectives, such as definitions,
    have few truly different questions.
  Where: ASSESSMENT.md sec 8.
  Why it matters: A re-check may sometimes resemble an earlier question.

R-024  [Medium]  The system cannot tell if the learner worked alone; using
       the Tutor during an attempt is not forbidden
  Problem: Attempts are assumed to be independent work. The Tutor must not
    give answers to an active assessment, but no spec stops the
    Orchestrator from running Tutor turns on the same objectives while an
    attempt is open.
  Where: TUTOR.md line 133; LEARNING_ORCHESTRATOR.md (no rule).
  Why it matters: Results could be inflated.

R-025  [Low]  There are no time limits, retake limits, maximum length or
       concurrency rules
  Problem: Undefined: how long an assessment may be, how many retakes are
    allowed, and whether two attempts can be open at once.
  Where: all specs (absent).
  Why it matters: Behaviour will differ between developers.

R-026  [Medium]  A wrong answer key cannot be disputed
  Problem: Generated answer keys can be wrong, and there is no way to
    report or correct one.
  Where: LEARNING_ORCHESTRATOR.md secs 4 and 10 (absent).
  Why it matters: A learner can be failed by a bad question.

R-027  [Low]  There is no human oversight
  Problem: No teacher or reviewer role exists. The IntelliCode paper
    recommends human educator guidance (PDF p. 7).
  Where: all specs (absent).
  Why it matters: Results should not be presented as official
    credentials.

R-028  [Low]  Accessibility and language needs are not specified
  Problem: ASSESSMENT.md accepts them as inputs, but Learning Context has
    no field for them.
  Where: ASSESSMENT.md sec 5; TUTOR.md line 52.
  Why it matters: Some learners cannot use the system fairly.

R-029  [Low]  There is no shared question bank
  Problem: Every question is generated fresh. This costs time and money
    and risks key errors.
  Where: ASSESSMENT.md sec 8.
  Why it matters: Cost and reliability. A bank can be added later.

R-030  [Medium]  There is no grade scale
  Problem: The Orchestrator talks about "grades" but defines no scale.
    ASSESSMENT.md proposes no numeric score, only pass, not passed or
    inconclusive, plus a status per objective.
  Where: LEARNING_ORCHESTRATOR.md lines 97 and 105.
  Why it matters: The UI and reports need to know what to show.

 3.3  The pre-planning diagnostic
-------------------------------------------------------------------------------

R-031  [Medium]  Choosing what the diagnostic tests overlaps with the
       Planner's job
  Problem: Before any curriculum exists, Assessment has to decide which
    areas to probe. That is close to choosing prerequisites, which is the
    Planner's job. ASSESSMENT.md limits this to areas taken from the goal
    preview milestones and from sources, and makes its suggestions
    advisory only.
  Where: LEARNING_PLANNER.md line 78; ASSESSMENT.md sec 7 step 2.
  Why it matters: Responsibilities between the two agents blur.

R-032  [Medium]  The diagnostic size is not agreed
  Problem: ASSESSMENT.md proposes one round of at most 10 questions,
    taken from the transcript's "5-10" suggestion. This was never
    confirmed.
  Where: ASSESSMENT.md sec 8; transcript_temp.txt lines 448-450.
  Why it matters: Too long annoys learners; too short tells the Planner
    little.

R-033  [Medium]  Diagnostic vs familiarity check: should results be
       reused?
  Problem: The two must stay separate. However, the Planner's familiarity
    check accepts "prior assessment evidence", so diagnostic results could
    be passed in.
  Where: LEARNING_PLANNER.md line 41.
  Why it matters: Passing them in could quietly merge the two steps.

R-034  [Low]  The Planner mentions "diagnostic answers" but has no
       diagnostic
  Problem: This is leftover wording from an earlier design.
  Where: LEARNING_PLANNER.md line 89.
  Why it matters: It is confusing to readers.

R-035  [Medium]  Diagnostic edge cases are not defined
  Problem: Undefined: what happens if the learner changes the goal after
    the diagnostic, whether it runs again after a replan, whether the
    learner sees the results, and how long results are kept. Stopping
    halfway is already handled in ASSESSMENT.md.
  Where: ASSESSMENT.md sec 10; LEARNING_ORCHESTRATOR.md (absent).
  Why it matters: Stale results could shape a new plan.

R-055  [Low]  The learner may be asked about their background three times
  Problem: Background questions can come up in three places:
    - in the goal preview's clarifications;
    - in the diagnostic;
    - at each course entry.
  Where: LEARNING_PLANNER.md line 39 and sec 7 step 5; ASSESSMENT.md
    sec 5.
  Why it matters: It adds friction, against the "learner-friendly" goal.

  Also NOT introduced:
    - no new agent and no agent-to-agent calls;
    - no database writes by Assessment;
    - no IRT, adaptive testing or Bayesian models;
    - no stack choice;
    - no invented pass percentage or duration.

5.2  The IntelliCode paper (2026.eacl-demo.10.pdf), used for ideas only
  Ideas taken, adapted to this project:
    - one writer that validates and commits updates (p. 2; already our
      rule);
    - stateless agents (p. 3);
    - fixed-rule checks plus judgement-based review (pp. 3-4);
    - assessment reports kept separate from learner-profile updates
      (pp. 3, 5);
    - recording misconceptions (p. 3);
    - feedback worded to the learner's level, never the grade (p. 4);
    - never revealing solutions during an attempt (pp. 6-7);
    - avoiding repeated questions (p. 4);
    - recording prompt versions (p. 10);
    - no personal data sent to agents (p. 8);
    - "unknown stays unknown" (pp. 3, 7).
  Ideas not taken:
    - six agents (p. 3);
    - POMDP maths (pp. 2, 9);
    - BKT/DKT numeric mastery scores (pp. 3, 9-10);
    - SM-2 spaced repetition (pp. 4, 10);
    - the 40/50/10 selection formula (p. 4);
    - counting self-reported skill toward proficiency (p. 10), which
      conflicts with our rules;
    - pass/fail-only scoring (p. 9);
    - five-level hints (p. 4; a possible Tutor idea);
    - its tech stack (p. 5);
    - its reported results (pp. 6-7), which come from 10 simulated
      learners and do not apply here;
    - engagement nudges (p. 5);
    - human-educator oversight (p. 7; see R-027).
